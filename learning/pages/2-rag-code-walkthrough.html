Redact personal data

app/redact.py:10 · PATTERNSapp/redact.py:23 · redact()called from app/pipeline.py:54

Before the ticket is searched, logged or sent to the LLM, regular expressions replace emails, phone numbers, IPs, employee/asset IDs and passwords with placeholders like [EMAIL]. We keep only the type of what was removed, never the value. Error codes such as 0x80070005 are deliberately kept because search needs them.

app/redact.pylines 10–35
PATTERNS: list[tuple[str, re.Pattern]] = [
    ("url_token", re.compile(r"(?i)https?://\S*?[?&](token|key|sig|code|auth|session)=\S+")),
    ("secret", re.compile(r"(?i)\b(password|passwd|pwd|pin|secret|api[_ -]?key|token)\s*(is|=|:)\s*\S+")),
    ("email", re.compile(r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b")),
    # … ip, ipv6, card, phone, employee_id, asset_id
]


def redact(text: str | None) -> tuple[str, list[str]]:
    """Return (clean_text, sorted list of redaction types found)."""
    if not text:
        return text or "", []
    found: set[str] = set()
    out = text
    for kind, pat in PATTERNS:
        def _sub(m: re.Match, kind: str = kind) -> str:
            found.add(kind)
            if kind == "secret":            # keep the label, hide the value
                return f"{m.group(1)}: [SECRET]"
            return f"[{kind.upper()}]"
        out = pat.sub(_sub, out)
    return out, sorted(found)

Turn the ticket into a meaning vector (embedding)

app/embeddings.py:25 · Embedderapp/embeddings.py:53 · encode()app/retriever.py:135 · embed_query()

The multilingual MiniLM model converts the text into 384 numbers that capture its meaning. Vectors are normalised to length 1, so cosine similarity is just a dot product. We embed the query once and reuse it for both ticket and KB search. The model loads from the laptop's cache first, so it works on bad Wi-Fi; if it can't load at all, a hashing fallback keeps the app alive.

4

Search past tickets: ChromaDB + BM25, then fuse the scores

app/retriever.py:138 · search_tickets():54 · to_where():192 · _semantic_candidates():208 · _hybrid()

Two searches run side by side and their candidates are merged:

  1. Semantic: ChromaDB's HNSW index returns the 30 vectors closest in meaning. Sidebar filters (status, app, dates…) become a Chroma where clause.
  2. Keyword: BM25 scores exact word matches, which matters for codes like 809 and product names like GlobalProtect. The same filter is applied.
  3. Fusion: every candidate gets 0.6·semantic + 0.3·bm25 + 0.1·meta, where meta = share of matching application/environment.

Watch out: BM25 raw scores have no fixed maximum, so we divide by the best score but never by less than 8 (BM25_FLOOR). Otherwise a weak keyword match would be stretched to 1.0, which is how the "coffee machine on floor 3" used to look like a printer ticket.

We run semantic search in ChromaDB and keyword search with BM25 under the same filters, then fuse them 0.6/0.3/0.1. Our evaluation showed hybrid beats either one alone.

Validate every claim in code

app/validator.py:20 · normalise():28 · excerpt_ok():53 · validate()app/pipeline.py:93 · retry once

Plain Python, no AI. For every quote: (1) was this source ID actually retrieved? (2) is the quote really inside that source, ignoring case, spacing and a leading "Resolution steps: 2."? A quote that fails is removed; a fix with no valid quote left is removed; labels outside the taxonomy are rejected. If every fix fails, the pipeline asks the LLM once more with the list of errors.

9

Decide: OK, NEEDS_REVIEW or ESCALATE

app/confidence.py:22 · retrieval_signal():30 · agreement_signal():44 · decide()

Three independent signals are combined, because an LLM's own confidence is often too high:

  • LLM (35%): the model's own confidence.
  • Retrieval (40%): how strong the evidence is: half the best KB score, half the average of the top 3 tickets (keyword-only matches don't count).
  • Agreement (25%): does the baseline agree with the LLM's category, multiplied by how many of the top 5 similar tickets share it.
app/confidence.pylines 22–27
def retrieval_signal(kb_hits: list[Hit], ticket_hits: list[Hit]) -> float:
    top_kb = kb_hits[0].score if kb_hits else 0.0
    # keyword-only matches don't count as real support
    tk = [h.score for h in ticket_hits if not h.score_breakdown.get("keyword_only")][:3]
    mean_t = sum(tk) / len(tk) if tk else 0.0
    return 0.5 * top_kb + 0.5 * mean_t

When the LLM is down (degraded mode)

If there's no key, every provider fails, or the UI's Use LLM switch is off, steps 6–8 are skipped. The baseline's label becomes the classification, and the top KB article's steps are shown word for word (so they are trivially valid evidence). The status can never be OK in this mode; the best it gets is NEEDS_REVIEW.
