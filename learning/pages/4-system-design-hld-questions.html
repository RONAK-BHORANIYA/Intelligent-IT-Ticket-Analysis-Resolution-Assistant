System Design Panel Prep

Questions judges ask about architecture: why each technology, how it scales, how it handles traffic and rate limits, and how it stays secure. Every answer starts from what we actually built and measured, then says how we would take it to production.

Method

Answer every design question in four beats

1 · What we didName the exact choice in our build.
2 · WhyThe constraint that drove it: 6 hours, no paid key, 7.8 GB laptop, needs filters…
3 · The limitWhere it breaks. Judges trust teams that know their limits.
4 · How we'd scale itThe production upgrade, behind the same interface.
Example: "Why SQLite?" We store the audit log in SQLite (what) because it needs zero setup and is one file, which suits a 6-hour build (why). It allows only one writer at a time, so it won't handle many API servers (limit). In production we'd move to PostgreSQL. Our db.py uses plain SQL with parameters, so the change is small (scale).

Throughput on the free tier
8,000 tokens/min ÷ about 2,700 tokens per ticket ≈ 3 tickets per minute per key → fine for a demo, not for a service desk.

A real service desk: 10,000 tickets/day
10,000 ÷ (8 working hours × 60) ≈ 21 tickets/min on average; Monday-morning peak ×3 ≈ 63 tickets/min
63 × 2,700 tokens ≈ 170,000 tokens/min → needs a paid tier with a higher limit, plus caching and duplicate collapsing.

Concurrency (Little's law)
in-flight requests = arrival rate × time each takes = (63 ÷ 60) per s × 2.5 s ≈ 3 at once → 2–3 API replicas are plenty; the LLM limit is the bottleneck, not our servers.

Vector memory at 1 million tickets
1,000,000 × 384 numbers × 4 bytes ≈ 1.5 GB of vectors, plus HNSW graph links → fits in RAM on one vector-DB node.

Re-embedding 1 million tickets
1,000,000 ÷ 85 per s ≈ 11,800 s ≈ 3.3 hours on one CPU → so we upsert only new tickets nightly, or use a GPU.

Retrieval takes 35 milliseconds; the LLM takes 2.5 seconds and is rate-limited. So we scale by protecting and reducing LLM calls (cache, duplicate collapsing, skipping the LLM when the classifier is very confident) far more than by adding servers.

AlgorithmHow it worksGood for
Fixed windowCount requests per clock minute; reset at :00Simple; allows a double burst at the window edge
Sliding windowCount requests in the last 60 sSmoother and fairer than fixed

Be careful with one answer: in the hackathon each teammate uses their own free key. In production you don't rotate many keys to get around a provider's limits; you buy the right tier. Judges notice the difference.
